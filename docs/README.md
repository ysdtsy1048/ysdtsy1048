### ■ データ基盤：運用改善（株式会社リクルート）

**期間：** 2022/4 〜 現在
**役割：** チームマネジメント／運用設計／改善施策立案／開発／運用・保守
**体制：** 3 名
**ステークホルダー：** TPM／SE／SRE／データ基盤利用者全般

#### 課題

- データ基盤の拡大に伴い、障害対応・リリース作業が **特定メンバーに依存**
- アラート・監視ルールが統一されておらず、
  - ノイズアラートが多い
  - 本質的な障害検知が遅延
- 日常運用に追われ、
  - 改善活動に割ける工数が慢性的に不足していた

#### 目的

- データ基盤運用を**属人対応から再現性のある運用へ移行**
- データエンジニアの認知負荷・突発対応を削減し、改善に集中できる状態を作る
- 障害対応を個人の経験値ではなくプロセスと仕組みで回る形にする

#### 実行内容

- **広義のデータリネージ活用による運用整理**
  - 上流データオーナー(マイクロサービスを運用・保守している SE)の明確化
    - メタデータ(テーブルラベル)への項目必須化
    - 上流テーブルスキーマ変更時のデータ基盤チームへの連絡を仕組化(緩いデータコントラクト)
  - 下流ステークホルダーの期待値の整理
    - 形骸化したジョブ・テーブルの棚卸
    - SLO 違反時の事業影響整理
    - 例: Adobe marketo
      - 日次 16:00 にカスタマーへのメール配信を実施
      - 最新の配信対象セグメントが不足している場合は機会損失につながる
      - 最新のオプトアウト者が反映できていない場合はインシデントにつながる(CX チームの個別対応が発生)

- **SLO 設計・整備**
  - データ基盤内の特定の外部システム連携・テーブル更新に対して delivery の SLO を定義
  - SLO 違反時のコミュニケーションパス・オペレーションをドキュメント化
    - 例: Adobe marketo
      - 14:00 までにデータ連携が正常に完了していること
      - 違反した場合は事前に定めた slack チャンネル・管轄チーム向けへ連絡すること

- **監視・通知の標準化**
  - コンピュートリソースアラート等の対応に繋がらないアラートの削減
  - 対応フローを添付した SLO アラートの追加

- **CI/CD・デプロイフローの改善**
  - CI による静的チェック・クエリテストを自動化
  - CD による Airflow, dataflow, CloudRun 等へのデプロイ自動化

- **ポストモーテム文化の定着**
  - 障害発生時に障害対応 issue を必ず作成・共有
  - 暫定対応のナレッジ蓄積に加えて、恒久対応の検討の俗人化を低減

#### 成果

- マージリードタイム：**~3 営業日 → ~1 営業日**
- 内的要因によるインシデント：通期 0 件
- ジュニア層も自主的に内部障害対応が行える状態を達成

### ■ データ基盤：dbt 導入（株式会社リクルート）

**期間：** 2024/10 〜 2025/10
**役割：** マネジメント／要件整理／設計／開発／既存クエリ移行／運用・保守
**体制：** メンバー 3 名
**ステークホルダー：** データ基盤利用者全般

#### 課題（定量的背景）

- クエリ依存関係・実行順序の手動管理による開発工数増
- データ品質を担保できていない
- CI/CD が最低限で目視レビューのため、レビュー品質を担保できていない

#### 目的

- 既存 SQL 群を dbt モデルへ移行し、
  **Transform レイヤーの依存関係をコードベースで一元管理**
- dbt test を中心とした検証プロセスを導入し、
  **Transform 層におけるデータ品質の自動担保**
- CI/CD を刷新し、
  **変更時の検知漏れ・手動確認コストを削減**
- 将来的なモデル・データソース増加に耐えうる
  **Transform 標準基盤の確立**

#### 実行内容

- **dbt 導入・モデル移行**
  - dbt モデル数：**700+**
  - dbt sources 定義数：**1,000+**
  - スキーマ YAML ファイル数：**1700+**

- **実行基盤の構築**
  - astronomer-cosmos により
    dbt モデル依存関係から Airflow DAG を自動生成

- **CI/CD の刷新**
  - CI/CD ワークフロー数：
    - Before：**9（Cloud Build）**
    - After：**30+（GitHub Actions）**
  - dbt 関連 CI：
    - dbt dryrun
    - dbt schema test
    - SQLFluff lint / format

- **データ品質管理**
  - dbt test 導入
  - delivery に関する SLO チェック DAG 導入

#### 成果

- SQL / Transform 変更時の
  - マージリードタイム：**~3 営業日 → ~1 営業日**
  - 障害発生件数：**10+/期 → 3+/期**
  - 障害リードタイム：**~5 営業日 → ~1 営業日**
- dbt を中心とした Transform/validation 実装が
  **組織内の標準実装パターンとして定着**

### ■ データ基盤：メタデータ整備（株式会社リクルート）

**期間：** 2024/10 〜 2025/10
**役割：** マネジメント／要件整理／設計／開発／運用・保守
**体制：** 3〜5 名
**ステークホルダー：** データ基盤利用者全般

#### 課題（定量的背景）

- Dataplex によるメタデータ管理を導入していたが、
  - 利用者の参照：**実質 Analytics Engineer 2 名の活用のみであることが調査とヒアリングから判明**
  - テーブル・カラム説明の記載率：**7%**
  と、実運用での活用が進んでいなかった
- クエリ内コメントや GitHub issue にはある程度仕様の記載があるが、それをメタデータとして転記するモチベーションがない
- データ利用者の独自スプレッドシートによるメタデータ管理が散見されていた

#### 目的

- 利用者が **データ探索〜理解〜利用までを自己解決**できるメタデータ基盤の構築
- メタデータ生成・更新を **CI/CD に組み込み、運用を自動化**

#### 実行内容（定量実績）

- **メタデータ基盤の再設計**
  - Dataplex を主軸とした運用から、
    **BigQuery 標準搭載の description をメイン、dbt docs を補助としたメタデータ提供基盤**へ移行
  - dbt モデル・sources をメタデータの SSOT として位置づけ

- **メタデータ自動生成**
  - Gemini API を用いた、カラム説明文の自動生成
    - 上流依存テーブルのメタデータの伝播
    - クエリコメントの吸い上げ
    - クエリロジックからカラム仕様の吸い上げ
    - `[自動生成]` をプレフィックスに付与し、ハルシネーションリスク対策

- **CI/CD 連動運用**
  - GitHub Actions（30+ ワークフロー）の一部として下記を実装
    - メタデータ生成
    - dbt docs ビルド・自動公開
    - メンテナーチームタグを required とし、チェック

#### 成果

- メタデータカバレッジ：**7% → 50%**
  - データレイク層のメタデータ記載が残課題
- 自動生成に伴って、メタデータ基盤として定着・自発的な取り組みを観測
  - メタデータ更新 PR：**10 件/月**
  - Gemini のプロンプト改修 PR も外部チームから発生

- センシティブデータに対し、
  - 分析用途での直接アクセスが技術的に可能な状態

- 自由記述カラム内の人名等、本来マスキングすべき項目の抜け漏れが発生

- センシティブデータを利用者が直接触れない前提のデータフローへ移行

  - 本番 DB への直接参照を排除し、s3 経由のファイル連携により代替
  - クラウド間通信は AssumeRole を採用し、クレデンシャルファイルレスな ETL を実現

- **Dataflow + Cloud DLP を用いたマスキング処理**
  - DLP API による
    - 高精度な個人情報検出
    - ルールベースに依存しないマスキング

#### 成果

- センシティブデータへの直接アクセスを完全に排除
- マスキング未対応項目の解消

### ■ スケーラブル CTR 予測システムの開発（株式会社 D2C）

**期間：** 2019/6 〜 2019/10
**役割：** 設計／モデル開発／システム開発（メンバー 2 名）
**ステークホルダー：** SE
**関連技術：** Amazon EKS / LightGBM / Python / Docker / Terraform / SNS / SQS / CircleCI

#### 課題

- メール型運用広告において CTR 予測モデルを活用したかったが、既存基盤では学習・推論処理が遅く、日次バッチ処理のスケールに限界があった
- キャンペーン数・配信量増加に伴い、モデル再学習・大量推論を安定して実行できる基盤が必要だった

#### 目的

- CTR 予測モデルを広告配信に組み込み、配信最適化・売上向上に貢献する
- 大量データに対して高速学習・高速推論可能な、スケーラブルな ML 基盤を構築する

#### 実行内容

- **スケーラブルな ML 実行基盤の設計・構築**
  - Amazon EKS を用いた Kubernetes ベースの実行基盤を設計
  - Docker による学習・推論ジョブのコンテナ化
  - SNS / SQS を用いた非同期ジョブ制御・キューイング設計
  - Terraform によるインフラ構成管理

- **CTR 予測モデルの開発**
  - LightGBM を用いた CTR 予測モデルを実装
  - 特徴量設計・ハイパーパラメータ調整を実施

- **プロダクトへの組み込み**
  - 予測結果を広告配信ロジックに組み込み
  - キャンペーン最適化に利用可能な形で提供

- **技術発信**
  - Kubernetes Meetup Tokyo #27 にて登壇: <https://www.slideshare.net/ToshiyaYoshida3/amazon-eksctr>

#### 成果

- CTR 予測基盤のスループットを大幅に改善 (推論処理時間：10h → 1h)
- CTR 予測を活用した配信最適化により、**売上向上（約 40%）に貢献**
- モデルの継続学習・運用が可能なスケーラブルな ML 基盤を確立
